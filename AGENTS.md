# Agent instructions

## Conventional Commits

Every commit message generated by an AI agent in this repository must follow
[Conventional Commits](https://www.conventionalcommits.org/). semantic-release uses these messages to determine versions
and release notes; see the [CI/CD and releasing guide](docs/ci-cd.md).

Use this subject format, with an optional scope and an optional breaking-change marker:

```text
<type>[optional scope][!]: <description>
```

Use a lowercase type and a concise, imperative description, for example `fix(pdf): preserve signature placement`.

| Type | Use for | Release effect |
| --- | --- | --- |
| `feat` | New application features | Minor |
| `fix` | Bug fixes | Patch |
| `perf` | Performance improvements | Patch |
| `docs`, `test`, `ci`, `build`, `chore`, `style`, `refactor` | Corresponding changes without a new feature, bug fix, or performance improvement | No release unless breaking |

Mark actual breaking changes with `!` before the colon (for example `feat(storage)!: change the agreement format`) or
a `BREAKING CHANGE:` footer. Explain the impact and migration in the commit body. Breaking changes trigger a major release.

Choose the type that accurately describes the change. Do not hide features or fixes under `chore`, or use `feat`/`fix`
solely to force a release. When generating PR titles or squash-merge commit messages, use the same convention so it
survives squash merging. Leave release versioning and tagging to semantic-release unless explicitly instructed otherwise.
